# EG-S3-SOURCE-001 — S3 факты, допуск действия и атомарная запись

**Решение владельца:** 2026-11-22 — разрешить корректное действие в активном S3 при `exposure=unknown`, не выдавая его за самостоятельную реакцию; состояние, первичные события и квитанция команды должны фиксироваться одной PostgreSQL-транзакцией. Это часть **чернового PR #25**. Слияние и запуск в Render не разрешены.

## Изменения относительно первоначального черновика

1. `adaptive/engine.js`: только для S3 снята проверка `delivery === confirmed` как условия **разрешения** действия. Для других сцен правило не изменено. Набор действий, последствия, лимиты, тексты и S4-переходы остаются прежними.
2. `adaptive/s3-source.js`: `presentation(..., confirmed)`, полученный от транспорта или симуляции, фиксируется как **заявление** `PRESENTATION_REPORTED`. В движок S3 передаётся `unknown`, а не недоказанное `confirmed`. Поэтому отправка Telegram и запись в журнал не устанавливают независимое наблюдение.
3. `adaptive/s3-postgres.js`: новый **репозиторий**, не новый сервер и не новая схема. Использует существующие `nablon_episodes`, `nablon_events`, `recordL0Event`. Запись событий `S3_CANONICAL_EVENT` и контрольного события `S3_COMMAND_RECEIPT`, содержащего состояние и квитанцию, выполняется между общими `BEGIN`/`COMMIT`. Запись/чтение сериализованы advisory-lock и проверкой сессии; после `ROLLBACK` квитанция не появляется. Повтор после `COMMIT` возвращает `REPLAYED`; тот же ID с иной командой — `CONFLICT`. Независимое `readPrimaryEvents` читает первичные строки отдельным запросом к PostgreSQL (не из присланного пакета).
4. Время записанных первичных событий для сверки Evidence Gate — **время самой PostgreSQL-строки**, а не время локального движка. `recordL0Event` использует транзакционный `NOW()`: одинаковые метки внутри одной транзакции допустимы; сомнение о реальном интервале означает `EXPOSURE_UNKNOWN`, не подтверждение.

Внутренняя `PRESENTATION_REPORTED` никогда не заменяет доверенного внешнего наблюдателя. Положительный вывод о самостоятельном реагировании без такого источника запрещён. При неопределённости `offer()` сохраняет ручной выбор ветки. Правила P2 о незавершённом эпизоде **не менялись**.

## Запуск проверок

Из корня Nablon:

```bash
node --test --test-reporter=tap adaptive/s3-source.test.js adaptive/s3-postgres.test.js
# Дополнительно, только с неизменённым intake.mjs из EG-INTEGRATION-P1-001:
EG_INTAKE_PATH=/path/to/intake.mjs node --test --test-reporter=tap adaptive/s3-source.intake.test.mjs
```

**Отдельный настоящий PostgreSQL-тест:** требуется `pg` из штатных зависимостей проекта, файл `schema.sql`, подготовленный **одноразовый** PostgreSQL-кластер и путь к закреплённому `intake.mjs`. Тест сам создаёт отдельную временную схему и удаляет её после проверки; не запускать против рабочей БД.

```powershell
$env:EG_S3_TEST_DATABASE_URL = 'postgresql://<test-user>:<password>@127.0.0.1:5432/<disposable-database>'
$env:EG_INTAKE_PATH = 'C:\path\to\EG-INTEGRATION-P1-001\intake.mjs'

```

Проверка инжектирует сбой **после первого** записанного факта, до квитанции, проверяет откат, единственное применение после повтора, `REPLAYED`, `CONFLICT`, первичную историю отдельным запросом и результат принятого Intake `EXPOSURE_UNKNOWN`.

## Критические ограничения до закрытия четырёх P1 рабочего S3

- **Нет рабочего Telegram-маршрута S3.** Унаследованный `bot.js` сохраняет `nablon_processed_updates` до вызова обработчика. Новый маршрут должен обходить именно эту преждевременную дедупликацию и передавать устойчивый ID команды в `execute()`. **Нельзя** просто подключить S3 после существующего middleware: повтор после отката будет потерян.
- На маршруте нужно сохранять подготовку исходящего сообщения в транзакции вместе с действием (переиспользовав существующий outbox), а отдельные сведения об отправке — вне транзакции доставки. Подтверждение Telegram API **не** доказывает предъявление.
- История S3 не порождает положительных свидетельств `exposure` и `help`; любые будущие свидетели должны иметь проверенные полномочия, точные ссылки на последствия и сопоставимые часы. Без них `unknown`.
- `s3-postgres.js` предполагает существующую сессию в `nablon_sessions` и создаёт собственную новую строку эпизода S3. Нужен контролируемый вызов из маршрута после фактического старта S3. Старый маршрут Nablon нельзя без проверки переиспользовать как есть.
- Долговременные записи через `nablon_events` используют полные снимки маленького S3 в квитанциях. Это минимизация изменений схемы, а не доказательство оптимальности для больших объёмов.
- **Четыре P1 рабочего S3 остаются открытыми, причинный допуск `BLOCKED`, Becoming/Render/main не затронуты.**

**Стоп-правило:** новая БД, новая логика классификации или новый Evidence Gate без обнаруженного необходимого основания запрещены. Переход к рабочему маршруту — отдельная проверяемая стадия этого же утверждённого объёма, не автоматическое разрешение выката.

## Telegram-переходы S2 → S3 → S4

`bot.js` регистрирует callback для S2 и S3 до общей дедупликации. Обработчик проверяет владельца и личный чат, передаёт идентификатор Telegram update в транзакционный репозиторий. Репозиторий проверяет номер хода и текущий эпизод под блокировкой. Повтор уже сохранённой команды старого эпизода может восстановить отправку. Новая команда со старой кнопки не меняет состояние. Остальные update идут в прежний обработчик.

Завершающее действие S2 и открытие S3 фиксируются одной транзакцией. По окончании S3 пользователю доступны S4A и S4B, включая случай `EXPOSURE_UNKNOWN`. Выбор сохраняется вместе с открытием выбранной сцены. События перехода и открытия ссылаются друг на друга через `nextEpisodeId` и `previousEventId`. Повтор возвращает прежний идентификатор эпизода. Правила хода и выбора остаются внутри исходного движка.

Запись в существующий `nablon_outbox` выполняется той же транзакцией, что и состояние, первичные события и квитанция. Для последствия ключ `s3:<eventId>` однозначно указывает на его каноническое событие. Отправитель обрабатывает очередь после COMMIT. При восстановлении существующий фоновый обработчик может обработать ожидающую запись. Telegram-отправка работает с повтором: если API принял сообщение, а запись `SENT` не состоялась, повтор отправки может показать сообщение ещё раз. Устойчивый ID команды и номер хода защищают журнал действий. Статус `SENT` не поступает в Evidence Gate как свидетельство предъявления.

Проверка ведётся с настоящими PostgreSQL и Telegraf, синтетическими update и подменённым Telegram API. Тест создаёт и удаляет собственную схему на одноразовом локальном кластере с параметром `cluster_name=eg-integration-p1-001`. Для запуска укажите `EG_S3_TEST_DATABASE_URL` и `EG_INTAKE_PATH`, как выше.

```sh
node --test --test-reporter=tap adaptive/s3-telegram.real.test.mjs adaptive/s3-postgres.real.test.mjs
```

Сквозная проверка начинается вызовом `openS2(context, state, commandId)` из тестового сервера. Он передаёт состояние, уже доведённое исходным движком до начала S2, с подтверждением предъявления от тестового источника. В действующем боте ещё нет вызывающего кода из предыдущей сцены и рабочего источника этого подтверждения. Успешная отправка через Telegram API его не устанавливает. Тест проходит S2 и S3 через Telegram callbacks, проверяет откат и восстановление с новым экземпляром Telegraf и пулом соединений, затем сохраняет выбранную сцену S4. Пользовательское прохождение самой S4 находится за границей этих двух переходов.
