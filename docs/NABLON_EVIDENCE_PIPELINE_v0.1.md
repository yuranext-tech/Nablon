# Nablon — Evidence Pipeline v0.1

## Status

Архитектурный контракт для перехода от экспериментального наблюдения к данным, которым может пользоваться Becoming.

Документ обобщает принцип Legitimate Uncertainty: недостаточность данных является валидным состоянием на любом уровне pipeline.

Это архитектурный принцип, а не доказанный научный механизм.

## 1. Pipeline

RAW OBSERVATION
↓
CODING
↓
SIGNAL CANDIDATE
↓
EVIDENCE GATE
├── REJECT
├── UNCERTAIN
└── EVIDENCE
        ↓
  ACCUMULATION
        ↓
CONTRAST / COUNTEREVIDENCE
        ↓
PATTERN HYPOTHESIS
        ↓
BECOMING

Becoming не должен строить пользовательские паттерны непосредственно из raw observations или неподтверждённых signal candidates.

## 2. Data statuses

| Status | Значение | Может поддерживать inference о пользователе? |
|---|---|---|
| RAW OBSERVATION | наблюдаемое поведение | нет |
| CODED | применение схемы разметки | нет |
| SIGNAL_CANDIDATE | потенциально значимый сигнал | нет |
| REJECT | сигнал непригоден для данного вывода | нет |
| UNCERTAIN | данных недостаточно для решения о пригодности | нет |
| EVIDENCE | прошёл условия допуска | да, в пределах заранее определённого вывода |
| PATTERN_HYPOTHESIS | накопленная рабочая гипотеза | да, только как гипотеза |

## 3. Legitimate Uncertainty

Система не обязана выбирать между «подтверждено» и «опровергнуто», если данных недостаточно.

UNCERTAIN должен сохраняться как отдельное состояние и не преобразовываться автоматически в EVIDENCE.

Это тот же архитектурный принцип, который в рантайме применяется к Legitimate Uncertainty / Settlement: недостаточные основания не являются основанием для принудительного вывода.

## 4. Design gate

До запуска участника каждая поверхность проходит pre-registered checklist.

Минимальные проверки:
- экспериментальный контраст действительно реализован;
- критерий результата понятен и наблюдаем;
- доступны необходимые варианты действий;
- нет очевидного единственного действия, объясняющего результат;
- сопоставима perceptual salience контрастных элементов;
- нет скрытой лексической подсказки;
- длина, число сущностей и сложность сопоставимы;
- специальные знания не являются скрытым условием;
- PROCESS_SWITCH можно отличить от изменения параметра;
- предусмотрены основные альтернативные объяснения.

Если checklist не выполнен, поверхность получает DESIGN_REJECT до сбора данных.

## 5. Runtime / collection gate

После сбора данных проверяются только фактически возникшие нарушения и непредвиденные проблемы:
- ошибка предъявления;
- технический сбой;
- потеря части последовательности;
- невозможность надёжно закодировать ход;
- обнаруженный confound, не покрытый design checklist;
- нарушение pre-registered условий.

REJECT после сбора не должен использоваться для ретроспективного спасения неудобного результата.

## 6. Calibration

Сам Evidence Gate является измерительным механизмом и должен быть калиброван до основной батареи.

### Positive control
Заведомо чистый сигнал.
Ожидание: EVIDENCE.

### Negative control
Заведомо загрязнённый сигнал с намеренно внесённым confound.
Ожидание: REJECT.

| Контроль | Ожидаемый статус | Если не сработал |
|---|---|---|
| Positive | EVIDENCE | gate слишком строг / правила неоперациональны |
| Negative | REJECT | gate слишком мягок |

Основная батарея не запускается, пока оба calibration controls не дают ожидаемый результат.

## 7. Coding reliability

Coding reliability и evidence validity — разные свойства.

Для экспериментальной единицы применяются два независимых слепых кодировщика. Cohen's kappa ≥ 0.70 используется как технический пилотный критерий согласованности, отдельно для action classes и PROCESS_SWITCH.

Низкая kappa означает проблему схемы кодирования. Она не означает «грязный пользовательский сигнал».

## 8. Evidence validity

После прохождения технического gate evidence всё ещё должно быть связано с конкретным выводом.

Проверяется:
- какой именно вывод допускает observation;
- какие альтернативные объяснения остаются;
- есть ли контрастное условие;
- есть ли counterevidence;
- повторяется ли observation в релевантных условиях;
- сохраняется ли provenance до исходного поведения.

Только после этого EVIDENCE может участвовать в accumulation для PATTERN_HYPOTHESIS.

## 9. UNCERTAIN feedback loop

UNCERTAIN не идёт в Becoming, но не теряется.

UNCERTAIN → aggregate by cell / contrast / failure reason → experiment quality → redesign.

Если UNCERTAIN систематически высок, нельзя просто увеличить N. Сначала нужно проверить, способен ли дизайн вообще дать различимый сигнал.

## 10. REJECT feedback loop

REJECT также не идёт в Becoming.

Причина REJECT должна сохраняться, чтобы отличать:
- плохой дизайн;
- нарушение исполнения;
- технический сбой;
- coding ambiguity;
- confound.

Это позволяет улучшать измерительный инструмент без изменения гипотезы под полученный результат.

## 11. Evidence → Becoming

Becoming получает не поток отдельных событий, а evidence с provenance.
Минимально должны сохраняться:
- исходное observation;
- experiment / cell / contrast;
- coding;
- причина допуска;
- известные ограничения;
- counterevidence, если оно уже существует.

PATTERN_HYPOTHESIS не является утверждением «пользователь такой». Это рабочее объяснение повторяющегося поведения в определённых условиях, которое может быть подтверждено, ослаблено или отвергнуто следующими наблюдениями.

## 12. Архитектурный инвариант

> Insufficient data is a legitimate state at every level of the Nablon pipeline.

Следствия:
1. плохой эксперимент не превращается в evidence;
2. неоднозначный сигнал не превращается в факт;
3. evidence не превращается автоматически в pattern;
4. pattern hypothesis не превращается автоматически в settled state;
5. недостаток данных не требует искусственного вывода только ради продолжения pipeline.

## 13. Отложено

- автоматическое принятие PATTERN_HYPOTHESIS как факта.
