# Nablon --- спецификация экспериментальной единицы v0.1

## 1. Назначение

Этот документ фиксирует, что именно наблюдается и как разметка отделяет
изменение способа обработки от простого изменения отдельного действия.

Это методологическая спецификация. Она не является доказательством того,
что выбранный конструкт валиден психологически.

## 2. Единица анализа

Минимальная атомарная последовательность:

**ход t → новая информация / изменение условий → ход t+1**

Пары используются для кодирования перехода. Полный эпизод состоит из
нескольких таких переходов и является единицей анализа поведения в
контексте.

## 3. Action classes

| Код | Определение |
|---|---|
| CONTINUE | Продолжение того же процесса без существенного изменения действия |
| PARAM | Изменение параметра, инструмента или среды внутри того же процесса |
| INFO | Получение нового факта: спросить, посмотреть, уточнить |
| TEST | Пробное действие, которое само даёт информацию о системе |
| RESTRUCTURE | Изменение процесса или источника получения результата |
| REEVALUATE | Остановка и переоценка цели, критерия или условий |
| ABANDON | Отказ от текущей цели или решения |

## 4. PROCESS_SWITCH

Отдельная бинарная переменная:

**YES** — следующий ход меняет процесс достижения результата, а не
только параметры текущего процесса.

**NO** — следующий ход остаётся внутри того же процесса.

Action class и PROCESS_SWITCH не являются одним и тем же признаком.

Пример принципа:
- INFO может быть INFO/NO, если человек просто уточняет параметр
  текущего процесса;
- INFO может быть INFO/YES, если получение информации означает переход
  к другому способу принятия решения.

Конкретные пограничные случаи должны быть зафиксированы до разметки
реальных экспериментальных данных.

## 5. Правило PARAM → RESTRUCTURE

Задаётся один вопрос:

> Меняет ли действие то, откуда и каким процессом получается требуемый
> результат, или меняет только настройки прежнего процесса?

Только первое считается RESTRUCTURE.

Пограничные случаи, где два кодировщика не могут применить правило
одинаково, не исправляются постфактум под результат эксперимента; они
используются для пересмотра схемы или исключения поверхности.

## 6. Process-trace

Дополнительный текстовый ответ участника может фиксироваться, но не
является доказательством причины действия.

Он может:
- помочь различить несколько возможных интерпретаций поведения;
- выявить непредвиденное понимание задания;
- показать осознанное объяснение.

Но постфактум объяснение не доказывает, что именно оно вызвало действие.

## 7. Информация между ходами

Для каждого перехода фиксируется источник изменения:

- EXTERNAL — информация предъявлена экспериментом;
- ACTION_GENERATED — информация получена как результат действия
  участника;
- SELF_REQUESTED — участник сам запросил информацию.

Это отдельное поле, не часть action class.

## 8. Длина последовательности

Минимум два хода после изменения условий допустимы для атомарного
перехода.

Полный эпизод не ограничивается двумя ходами: существенное переключение
может произойти после нескольких промежуточных действий.

Поэтому:

**пара ходов = единица кодирования; эпизод = единица анализа.**

## 9. Слепая разметка

Кодировщик не знает:
- условие C1/C2/C3/C4;
- фазу эксперимента;
- ожидаемый signal;
- результат участника;
- гипотезу конкретной клетки.

Кодировщик получает только необходимый фрагмент поведения и контекст,
достаточный для применения правил.

## 10. Пилот разметки

До проектирования поверхностей собираются 8–10 коротких бытовых
переходов.

Обязательно включить спорные случаи:
- PARAM vs RESTRUCTURE;
- INFO/NO vs INFO/YES;
- TEST vs INFO;
- REEVALUATE vs RESTRUCTURE;
- RESTRUCTURE vs ABANDON.

Два кодировщика работают независимо.

## 11. Критерий приёмки

Для пилота используется ориентир:

**Cohen's kappa ≥ 0.70** отдельно:
- по action classes;
- по PROCESS_SWITCH.

Это критерий технической согласованности разметки, а не доказательство
валидности конструкта.

При низком согласии:
1. смотрим матрицу разногласий;
2. находим систематически смешиваемые классы;
3. меняем определение или правило;
4. повторяем пилот.

Не начинаем исправлять будущие сценарии под уже неудобную схему.

## 12. Confound audit

Для каждого перехода до включения в корпус задаются:

- может ли такое же поведение возникнуть без изменения способа
  обработки;
- может ли отсутствие переключения означать, что участник просто не
  заметил обстоятельство;
- может ли действие объясняться личным предпочтением;
- может ли оно быть следствием очевидной единственной стратегии;
- не измеряем ли мы смекалку, внимание или знание формата вместо
  выбора способа обработки.

Если альтернативное объяснение нельзя отличить по наблюдаемым данным,
переход не считается чистым измерением PROCESS_SWITCH.

## 13. Relation to K1–K3

K1–K3 задают условия эксперимента. Они не определяют саму разметку.

- K1: нарушение / ненарушение критерия;
- K2: текущий способ недостаточен / локальная коррекция достаточна;
- K3: обстоятельство релевантно / нерелевантно результату.

Сначала принимается единица разметки. Затем проверяется, позволяют ли
конкретные поверхности создавать чистые контрасты K1–K3.

## 14. Запрет на post-hoc рационализацию

До просмотра результатов для каждой экспериментальной клетки должны быть
записаны:
- ожидаемый signal;
- ожидаемый anti-signal;
- какие наблюдения противоречат гипотезе;
- какие наблюдения считаются неоднозначными;
- когда клетка будет признана непригодной.

После получения данных эти правила не меняются для спасения результата.

## 15. Что эта спецификация пока не утверждает

Она не утверждает:
- что PROCESS_SWITCH равен «обучению»;
- что переключение всегда полезно;
- что отсутствие переключения является ошибкой;
- что семь классов являются полной моделью человеческой обработки;
- что переход в RESTRUCTURE/REEVALUATE/ABANDON обязательно является
  более мощным режимом.

Она только создаёт технический способ наблюдать и кодировать изменение
обработки, который затем можно подвергнуть экспериментальной проверке.
