# Nablon — Evidence Gate calibration and coding pilot v0.1

## Status

Технический пилот измерительного фундамента перед разработкой основной батареи EXP-001.

Цель: проверить две вещи отдельно:
1. способен ли Evidence Gate различать EVIDENCE / REJECT / UNCERTAIN на заранее сконструированных контролях;
2. способны ли независимые кодировщики надёжно различать action class и PROCESS_SWITCH.

Это не эксперимент на эффективность Nablon и не evidence о пользователе.

## 1. Gate calibration

Используются три контрольных типа.

| Control | Намеренно заданное состояние | Ожидаемый статус |
|---|---|---|
| POSITIVE | confounds контролируемы; сигнал пригоден для конкретного вывода | EVIDENCE |
| NEGATIVE | заранее внесён существенный confound | REJECT |
| BORDERLINE | данных недостаточно для легитимного решения | UNCERTAIN |

Gate считается калиброванным для пилота только если все три контроля получают ожидаемые статусы по заранее записанным правилам.

### Positive control

Это не «хороший ответ участника», а контрольный объект для самого gate. Все заранее заданные условия допуска известны и выполнены: контраст реализован, критерий результата наблюдаем, альтернативные пути существуют, perceptual salience сопоставима, скрытых подсказок и специальных знаний нет, provenance полного перехода сохранён.

Для заранее определённого вывода gate должен признать observation пригодным.

Ожидаемый статус: EVIDENCE.

### Negative control

Это контрольный объект с заранее внесённым нарушением одного существенного условия допуска. Например, в одной клетке намеренно отсутствует реальная альтернатива, хотя интерпретация сигнала требует сравнения альтернативных способов обработки.

Поскольку требуемый вывод больше не идентифицируем по наблюдаемому поведению, gate обязан остановить его.

Ожидаемый статус: REJECT.

### Borderline control

Это контрольный объект, в котором заранее оставлено ровно такое количество неопределённости, при котором ни EVIDENCE, ни REJECT не оправданы. Например, provenance перехода неполон, но не настолько, чтобы считать весь эпизод недействительным.

Gate не должен придумывать недостающую информацию.

Ожидаемый статус: UNCERTAIN.

## 2. Coding pilot

Кодируются переходы move t → new information → move t+1.

Action classes:

1. CONTINUE — продолжение того же процесса без изменения.
2. PARAM — изменение параметра, инструмента или среды внутри того же процесса.
3. INFO — получение нового факта.
4. TEST — пробное действие, которое само даёт информацию о системе.
5. RESTRUCTURE — изменение процесса или источника получения результата.
6. REEVALUATE — остановка и повторная оценка цели, критерия или условий.
7. ABANDON — отказ от цели или выбранного решения.

Отдельно кодируется PROCESS_SWITCH = YES / NO.

Правило PARAM / RESTRUCTURE: если меняется то, где или как производится результат, это RESTRUCTURE; если меняются только настройки того же процесса — PARAM.

INFO не считается автоматически ни switch, ни non-switch. Кодируется по вопросу: изменило ли получение информации сам способ достижения результата.

## 4. Что здесь специально проверяется

- T03 и T07 разделяют INFO/NO и INFO/YES.
- T02, T06 и T08 проверяют PARAM без перехода процесса.
- T04 и T10 проверяют RESTRUCTURE.
- T05 и T09 проверяют разные формы REEVALUATE/RESTRUCTURE.
- T11 проверяет TEST без switch.
- T12 проверяет ABANDON.

## 5. Blind coding procedure

Кодировщики получают только Move t, new information и Move t+1. Они не получают expected class, expected switch и не знают, к какому контрасту относится переход.

Сначала каждый кодировщик независимо указывает:
- action class;
- PROCESS_SWITCH;
- краткую причину классификации;
- если есть ambiguity — границу, вызвавшую сомнение.

После независимого кодирования сравниваются:
- Cohen's kappa для action class;
- Cohen's kappa для PROCESS_SWITCH;
- confusion matrix;
- все случаи расхождения.

Целевой технический порог пилота: kappa ≥ 0.70. Это диагностический порог схемы coding, а не доказательство валидности конструкта.

Особое внимание:
- PARAM ↔ RESTRUCTURE;
- INFO ↔ REEVALUATE;
- TEST ↔ INFO;
- PROCESS_SWITCH при INFO.

## 6. Правило остановки пилота

Если кодировщики систематически расходятся, не переписывать отдельные переходы до получения удобного результата.

Сначала фиксируется причина расхождения. Затем изменяется правило классификации или сам набор классов. После изменения проводится новый blind coding.

Если gate не проходит calibration controls, основная батарея EXP-001 не запускается.

Если coding не достигает технического порога, разработка поверхностей EXP-001 приостанавливается до исправления схемы coding.

## 7. Что этот документ НЕ доказывает

- что PROCESS_SWITCH является валидным измерением общего когнитивного навыка;
- что человек обучился;
- что существует устойчивый пользовательский паттерн;
- что Becoming должен создать какой-либо паттерн;
- что положительный calibration result означает эффективность Nablon.

Этот документ проверяет только измерительный фундамент, на котором следующие утверждения вообще можно будет проверять.
