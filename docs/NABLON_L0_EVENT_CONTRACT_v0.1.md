# Nablon L0 Event Contract v0.1

Status: working implementation contract
Date: 2026-09-23

## Purpose

L0 is the immutable factual event stream produced by Nablon.

L0 records what the runtime presented, what the user did, and what the runtime technically did.

L0 does not contain:
- cognitive judgments;
- skill scores;
- hypotheses;
- outcome judgments;
- diagnoses;
- inferred motives;
- permanent user traits.

Those belong to Becoming's interpretation layer.

## Event envelope

Every learning-relevant L0 event has:

- event_id: database-generated immutable identifier
- event_name: stable event type
- occurred_at: timestamp generated by the server
- user_id: Nablon user reference
- session_id: Nablon session reference
- episode_id: Nablon episode reference when applicable
- set_id: stable content-set identifier when applicable
- scenario_id: stable scenario identifier when applicable
- turn_index: episode-local sequence number
- program_version: version of the program/content definition
- runtime_version: version of the Nablon runtime
- payload: event-specific raw data

The envelope must remain stable even when program content changes.

## Initial event vocabulary

### Session / episode lifecycle

SESSION_STARTED
SESSION_COMPLETED
SESSION_ABANDONED
EPISODE_STARTED
EPISODE_COMPLETED
EPISODE_ABANDONED

### Presentation

PROBE_PRESENTED
SCENARIO_PRESENTED
INTERVENTION_PRESENTED
SUPPORT_PRESENTED
TRANSFER_PRESENTED

### User actions

USER_RESPONSE
USER_ACTION
USER_REQUESTED_HELP
USER_STOPPED

### Runtime facts

DELIVERY_SUCCEEDED
DELIVERY_FAILED
RUNTIME_ERROR

This vocabulary is deliberately small. New event types require a reason; event payload should not become an unstructured substitute for stable event semantics.

## What belongs in payload

Payload may contain exact raw material needed to reconstruct the interaction, for example:

- exact presented text;
- exact user text;
- selected button/action;
- stable content identifiers;
- delivery metadata;
- Telegram message/update identifiers where operationally useful;
- support text shown;
- response metadata.

Do not put derived labels such as "user chose analysis mode" into USER_RESPONSE.

## Versioning

program_version identifies the content/program version used for the interaction.

runtime_version identifies the execution runtime version.

Changing either must not rewrite historical events.

## Ordering and idempotency

Events are append-only.

The database timestamp is authoritative for storage time. The client timestamp, if retained, is metadata only.

Telegram update identifiers may be stored for deduplication, but Telegram update identity is not the L0 event identity.

Repeated delivery of the same Telegram update must not create duplicate user-action events.

## Provenance

Every interpretation produced later by Becoming must be able to point back to the L0 events on which it relies.

Therefore L0 event identifiers must be stable and never reused.

## Privacy / minimization

Store what is necessary to reconstruct the experiment and evaluate it later.

Do not store inferred sensitive attributes or unnecessary personal data in L0.

## Boundary

Nablon writes L0.

Becoming reads L0 and produces interpretation, evidence, hypotheses, outcome assessments, and next-program decisions.
